# التوسعة لمشروعات SaaS القادمة

المشروع يستخدم قاعدة MySQL واحدة. كل مستخدم أو دور تابع لعميل يحمل `tenant_id`، بينما فريق المنصة يحمل قيمة `null`. عضوية المستخدم تحدد نطاقه؛ لا يعتمد الخادم على `tenant_id` يرسله المتصفح لاختيار العميل.

`User::canDo()` هو مدخل فحص الصلاحيات. `is_super_admin` مخصص لحساب المنصة الرئيسي، و`Role::is_owner` يحمي دور مالك العميل. صلاحيات العميل تقتصر على إدارة المستخدمين والأدوار؛ إدارة العملاء وإرسال الإشعارات العامة تخص المنصة. تنطبق القيود على الطلبات في الخادم بجانب إخفاء الأزرار في الواجهة.

| `resources/views/partials/navigation.blade.php` | مجموعات التنقل المشتركة بين القائمة الجانبية والأفقية، مع فحص الصلاحيات. |
| `resources/views/partials/appearance.blade.php` | خيارات عرض القائمة والثيم واللغة في البروفايل. |

## إضافة وحدة أعمال

1. أنشئ جدولًا مثل `projects` مع `tenant_id` مرتبط بالعميل وفهرس مناسب. احتفظ بعمليات العميل داخل نطاق عضويته.
2. أضف الصلاحيات مثل `projects.view` و`projects.create` إلى إعداد الصلاحيات ونصوص اللغات الخمس، ثم راجع منحها لدور المالك.
3. احمِ الروابط بالمصادقة والصلاحية المناسبة، وطبّق نطاق `tenant_id` في كل استعلام للعرض أو التعديل أو الحذف أو البحث أو التصدير.
4. استخدم Blade والقالب العام و`<x-icon>`، ومرّر رسائل النجاح عبر session لكي تظهر Toast تلقائيًا.
5. أضف الرابط إلى مجموعة مناسبة في `partials/navigation.blade.php` عند امتلاك الصلاحية؛ سيظهر في التنقل الجانبي والأفقي. ثم أضف مؤشرات حقيقية للـDashboard الفارغة.
6. أضف اختبارًا يثبت أن عميلًا آخر لا يمكنه الوصول للسجل حتى باستخدام رقمه الصحيح في الرابط.

لا توسع قبول حقول الطلب بـ`request()->all()` لتحديث User أو Role؛ احتفظ بقائمة حقول مصرح بها، وعيّن النطاق والحقول الحساسة من الخادم. إذا أضفت jobs أو exports أو API endpoints، طبّق نفس العزل داخلها.

حقل `users.layout` يقبل `vertical` أو `horizontal` ويُحدَّث عبر `/preferences` لصاحب الجلسة فقط. التفضيل يخص المستخدم ويستمر عند تسجيل الدخول من متصفح آخر. تغيير اللغة أو الثيم وحدهما لا يعيد ضبط شكل القائمة.

التنسيق يستخدم متغيرات CSS موحدة في `public/assets/app.css` وخط Cairo المتغير المحلي المرخص في `public/assets/fonts.css`. لا توجد مرحلة بناء للواجهة. القوائم المخصصة في `app.js` تحتفظ بعنصر `select` الأصلي لقيم الطلب والتحقق، وتضيف واجهة قابلة للاستخدام بلوحة المفاتيح. استخدم الأصناف والمكونات المشتركة للصفحات الجديدة.

إعدادات البيزنس لها `scope` فريد يُشتق من المستخدم المصادق عليه: `platform` أو `tenant-{id}`. لا يقبل الخادم اختيار نطاق آخر من الطلب. إدارة General تتطلب `settings.manage`، بينما SMTP يشترط `is_super_admin` وكون الحساب من فريق المنصة مباشرة، ولا توجد صلاحية SMTP يمكن منحها لدور عميل. بيانات General تخص الهوية التجارية؛ سجل العميل الإداري الموجود في `tenants` يبقى مستقلًا.

ملفات اللوجو الخاصة داخل `storage/app/private/workspace-logos`، بأسماء عشوائية وامتداد مشتق من نوع الصورة. مسار `/settings/logo` يختار ملف مساحة المستخدم فقط. التنظيف بعد الاستبدال أو الحذف ينتظر نجاح المعاملة؛ حذف العميل عبر `ClientController` يحذف سجل إعداداته وملفه كذلك.

SMTP يُحمَّل عند استخدام مدير البريد بدل قراءة قاعدة البيانات أثناء boot أو كتابة كلمات المرور في كاش الإعدادات. الوضع المفعّل يستخدم ناقل `platform_smtp`؛ تعطيله يعيد إعدادات البيئة. يتطلب نقل قاعدة البيانات المشفرة الاحتفاظ بـ`APP_KEY`. مراجع التنفيذ: [إعداد البريد في Laravel](https://laravel.com/docs/12.x/mail#configuration)، [Encrypted Casting](https://laravel.com/docs/12.x/eloquent-mutators#encrypted-casting).

الإشعارات الحالية تعتمد على قاعدة البيانات وpolling في المتصفح، لذلك لا تحتاج خادم WebSocket. إضافة مزود دفع أو فواتير أو تكامل بريد تسويقي أو ملفات عامة أو اشتراكات مدفوعة تكون وحدة مستقلة فوق هذا الأساس.
